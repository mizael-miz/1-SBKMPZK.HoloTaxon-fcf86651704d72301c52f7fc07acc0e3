Verdicts
Adjudication item 1 — "H2 confirmed-live (silent-undefined sandbox require)": CONFIRM, confidence 0.90. [E] E1 (loader error "Failed to load plugin holotaxon. No exports detected.", eval completed) + E3 (require("./dist/main.js") returned undefined, no exception) + E4 (module.exports assignment works in the real loader) triangulate cleanly: on Android the injected require does not resolve relative paths and fails silently to undefined rather than throwing. Correction to my Round-1 report: I predicted an Android throw ("Cannot find module './dist/main.js'" or a ReferenceError) — the live mechanism is silent-undefined, not a throw [I]. The substance of H2 (relative require cannot resolve in Obsidian's eval context) is confirmed; my predicted error string for Android was wrong and is hereby withdrawn. The 0.10 held back: the silent-undefined mechanism is established for Android only; this artifact's desktop behavior (throw with renderer_init stack) remains a prediction, not a live observation [E: desktop never tested].
Adjudication item 2 — "H1 refuted-live": CONFIRM, confidence 0.85 — with a scope caveat that matters. [E] The failure occurred at module evaluation: the require returned undefined, so module.exports was never populated and the loader's export check never saw a namespace shape to accept or reject. H1's premise ("Obsidian requires the constructor directly on module.exports") was never actually exercised by this failure. E4 proves the direct-class export loads. Caveat: E4 does NOT prove the namespace shape ({__esModule, default, named exports}) is acceptable on Android — the probe used module.exports = class, while the esbuild CJS bundle will ship the namespace shape. H1 is refuted-live as the cause of this failure; the narrower claim "the namespace shape would also have loaded" remains untested and is falsifier F1 below.
Adjudication item 3 — "H3 eliminated": CONFIRM, confidence 0.95. [E] E2 shows dist/ present and the 99-byte stub in place; combined with E1 (the plugin was found, evaluated, and reached the export check), the install layout was correct. H3 is dead for this install.
Adjudication item 4 — "fix = self-contained bundle, pre-validated by E4": CONFIRM the direction, CONTEST "pre-validated", confidence 0.75. The single-file bundle is the right fix (matches the official contract: bundle all dependencies into main.js — obsidian-api README). But E4 validates only: eval works, require("obsidian") works, direct-class module.exports works. It does not validate the esbuild bundle's namespace export shape, the full plugin lifecycle, styles.css, cold-start load, or the CI-produced artifact itself. The G0/S0 gate must stay BLOCKED until the actual bundled artifact passes a live install.

Consistent with Licat's statement that Obsidian "only load[s] main.js using eval as a string so it doesn't actually load from your file path" (Obsidian Forum).
[K] Obsidian intercepts requires during plugin load for mobile-supported plugins: "Obsidian raises an 'attempted to load NodeJS package' warning (as a Notice toast and a console.error) whenever a require('fs'|'path'|'crypto'|'url'|…) runs at plugin load" (obsidian-gemini testing docs). This is documented proof that the loader's require is wrapped and non-throwing for at least node builtins — consistent with, though not proof of, the silent-undefined behavior for relative paths.

[K] Mobile has no Node.js/Electron APIs; calls crash plugins (Obsidian Mobile docs).

F2 (artifact identity): install the artifact downloaded from the CI run (not a local rebuild), so the test covers exactly what CI certified.
F3 (lifecycle): enable → onload runs (observable effect or log), disable → onunload, re-enable, and a cold load after full app restart (startup load path may differ from the settings-toggle path).
F4 (packaging completeness): styles.css applied; manifest gating passes (installed app version ≥ minAppVersion 1.5.0 — the app version is still unrecorded [E]).
F5 (desktop): load the same artifact on desktop — never yet tested for any build of this project.
F6 (no stray requires): the bundle contains no require("fs")-style node-builtin calls; on mobile these trigger Obsidian's "attempted to load NodeJS package" warning rather than a crash (obsidian-gemini docs), which could mask a latent defect.
Q2 — Withdraw or defend H1 (LUMO's question)
Withdraw H1 as the causal diagnosis. [I] The defense is untenable: E3's TypeError proves the required module content was undefined, so no export shape ever reached the loader — the loader's complaint (E1) was absence of exports, not malformed exports. E4 removes the residual doubt that a valid direct export loads. However, withdrawing H1-as-cause must not be over-read: it does not establish that the esbuild namespace shape is acceptable on Android — that is exactly falsifier F1, and the bundle install must close it. If LUMO's H1 was the narrower claim "the namespace shape would have failed anyway," that claim is neither confirmed nor refuted by E1–E4; it is untested.
Q3 — Documented source contradicting "mobile's injected require returns undefined for relative paths silently"?
No contradicting source found. [K] Searched Obsidian docs, forum, GitHub issues, and community plugin docs. Findings: (a) no official documentation describes the mobile require shim's behavior at all — it lives in minified app.js, so the silent-undefined mechanism is undocumented either way [I]; (b) the closest documented behavior, Obsidian's "attempted to load NodeJS package" warning for node-built-in requires at plugin load (obsidian-gemini docs), shows a wrapped, non-throwing require — mildly corroborating, not contradicting; (c) the Templater Android case (issue #223) shows the same symptom class. Verdict: the claim stands on the live probe evidence (E3) alone; it has no documentary support and no documentary contradiction. Treat it as an observed-but-undocumented platform behavior, and do not encode it into guards as if it were contractual.
